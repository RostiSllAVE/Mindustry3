# Task 3 — Elevated turret combat and player control, 0.16.0

Read the complete supplied task before edits. Continued the clean `feature/ui-polish` checkout at `c2319213cec25371f93bde202066ab89f0948acb`. Existing layered construction, logistics, structural collapse, terrain, flying AI and unit models remain in place. No turret recipes, damage/range settings or new weapon/block definitions were introduced.

## Confirmed causes

1. Upper turret wrappers explicitly returned `canControl=false`, and their target validator required a non-null enemy even during player/logic control. Native `TurretBuild` deliberately allows those control paths without an automatic target.
2. A descending projectile could immediately intersect the emitting upper turret's own solid volume. Actual unfixed 160.7 SDL reproduction: Duo at Z3 acquired the enemy, fired 25 shots, consumed ammo 60→35, but caused **0 damage** and could not be controlled. Evidence: `local/layer-smoke/elevated-turrets-before-1607/layers-result.json`. With the shared collision correction, the same scene caused **207 damage** through ordinary ammo/weapon rules (`local/layer-smoke/elevated-turrets-first-1607/layers-result.json`). No damage setting was raised.
3. Possession picking resolved buildings only through native XY tiles. The fixed player pose also used the Z0 surface. Native `TypeIO.writeUnit/readUnit` sends a controlled building unit by XY position only; an elevated turret could otherwise decode as the ground turret underneath.
4. Upper acquisition depended on the FPV presentation flag. Switching back to native 2D could deactivate the common XYZ bullet adapters. A cached upper-turret count now keeps that existing combat pipeline active while upper turrets are present.

## Focused implementation

- Existing native upper `ItemTurret`, `LiquidTurret`, `PowerTurret`, `LaserTurret`, `ContinuousTurret` and `ContinuousLiquidTurret` wrappers still inherit native update/reload/consumers/shoot patterns. They now permit the native player-control capability and distinguish controlled/logic firing from automatic enemy validation. Automatic validation uses native invalid-target checks, filters, air/ground restrictions and existing XYZ range/occlusion/prediction.
- The shared projected-defense boundary accepts optional emitter context. Only the exact emitting building's own upper hull is excluded; the same targeting/projectile/beam/lightning pipeline still stops on other solids, shields and real platforms. Other callers retain their old query behavior. This fixes downward fire without giving shots general wall penetration.
- `TurretMuzzle3D` rotates the original forward/lateral barrel offsets into the actual firing pitch and preserves a safe position above the construction base. Persistent beams refresh that muzzle every update. Existing projectile gravity, ballistic arcs, range falloff, laser rules, damage and ammunition remain the source of truth.
- `LayerTurretControl` uses validated stable construction IDs, native possession/team/admin rules and stationary native building-unit proxies. Existing Ctrl-click picking reaches upper buildings through their physical query; ordinary unit/Z0 possession still uses the native RPC. Existing V/respawn binding releases upper control once. Releasing/destroying/detaching/changing team restores the previous live available unit, otherwise ordinary core respawn is used. Manual control uses the existing authenticated aim/fire inputs and native weapon loop; no extra firing simulation is introduced.
- `LayerTurretUnit` remains a native `BlockUnitUnit`. Its real tile field controls validity/damage/position. A small public wire view returns an invalid ground-grid position solely for native unit serialization, preventing Z0 aliasing. Actual building/tile packed coordinates and power/logistics references are unchanged. Its team setter cannot mutate a real turret when a player changes teams.
- Multiplayer adds two actions and one bounded state channel to the existing authenticated protocol/framing. The server alone possesses, consumes ammo, fires and damages. The channel synchronizes stable building/player/proxy IDs and yaw/pitch; a chained native client entity-snapshot hook reapplies valid upper bindings after their deliberately null native wire reference. Existing epoch/sequence/replay and matching-JAR checks remain. The prior packet listener is restored on close.
- The current renderer keeps the cached fixed turret base and pitches native gun art as a plane. Native drawer previews/full icons provide a fallback for composite guns without a standalone region. Zero-pitch UV/yaw matches the existing atlas geometry. Culling includes the pitched gun tips; source assets remain in the player's game atlas.

## Use

Enter **Tab / Build**, clear any selected construction block/schematic, aim at the visible friendly turret and press **Ctrl + LMB**. Exit Build Mode to aim with the FPV camera and fire with LMB. Translation/climb/creator-flight inputs cannot move the turret. **V**, or the configured standard respawn/release binding, relinquishes control. Ordinary unit switching remains available.

Multiplayer requires the same updated JAR for server and all players. Ownership is transient: save/load preserves native ammo/liquids/power/reload/heading/building state, ends possession and resumes normal AI after reacquisition.

## Remaining limits

- Existing audited native upper families are supported; this pass does not add arbitrary third-party building factories or a new adapter for unsupported payload-ammunition turrets such as Scathe. Non-controllable vanilla defenses/repair buildings keep their original controllability.
- Existing native XY AI/pathfinding and logic instruction interfaces remain; no new XYZ logic instruction set was introduced. Automatic acquisition retains the current conservative terrain/solid line-of-sight policy, even for artillery; projectile ballistic physics remain unchanged.
- Gun art is a pitched native textured plane over the existing building volume, not a new articulated turret model or independent barrel collider. Some multipart detail/glow animations are still represented by cached native previews rather than individual moving 3D parts.
- Controller ownership is intentionally not persisted in save files. A previous unit that died, disappeared or became controlled by someone else cannot be reclaimed; core respawn is the fallback.
